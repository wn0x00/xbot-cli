# 维护执行流程

## 确认范围和身份

从用户请求、已有日志和附件提取资产、故障版本、输入、预期、实际、失败行/块及已获授权。未知项保留 unknown；只读调查可以先推进，不要求所有字段齐全。

- 只读调查：读取、分析；不运行或修改业务。
- 仅复现：按授权重建前置并运行原逻辑，不修改正式业务实现；必要的临时辅助见 [临时变更](temporary-values.md)。
- 完整维护：连续进行调查、最小修复及验证，不逐步重复询问；发布、同步及业务副作用仍按具体范围判断。
- 仅验证：验证指定候选，不顺手修复或重构。

查实际 CLI 及相关通道状态。已有资产 ID 时优先客户端直接读取/打开，不先全盘找源码。只读调查可使用受支持的查看模式或既有只读资料；需要保存时进入编辑模式。打开/切换前保护当前草稿，不强制抢占。

按需要区分市场/官方资产标识、安装 ID、Studio app_id；记录用户故障版、在线版、当前编辑基线及来源。当前编辑版可以用于获准测试，但不能冒充故障旧版；未取得旧版就限定结论。详见 [环境映射](environment-and-paths.md)。

## 还原有效条件

读真实入口、参数和上下游调用，明确本次输入被哪里消费。既有 test() 固定值、提前 return/exit、对象来源都要核对，不把“参数已写入”当作已用到本次执行。优先现场支持的运行输入，不能传值时按授权建立可恢复临时条件。

元素故障先按 [元素出现条件](element-preconditions.md) 从代码推导前置，确认页面/窗口、账号、业务记录和状态后再讨论定位；按 [平台识别](../references/automation-routing.md) 选择模块。现有活动窗口或当前页面不证明已到达目标状态。

复现 Flow 缺陷优先走原入口/原调用链。CLI 直接 Web/Win32 观察或获准辅助动作可诊断、准备条件，但报告必须区分辅助诊断与完整 Flow 复现，不用手工成功代替原流程成功。不清除用户会话或关闭他人窗口来“重置”。浏览器按 [选择规则](browser-policy.md)，测试路径按环境映射。

## 运行与根因

先做一次有效尝试；间歇问题才制定有界次数/时长及停止条件。用户预算优先，团队可约定例如最多三次；没有固定通用次数。每次续试须有明确假设、上一轮终态和重复安全依据。unknown/超时只续查原 run_id/task_id 与业务结果，不新启一轮。

缺必填对象、没到失败路径、运行到另一错误分别记录；不能用这些结果写“原故障未复现”。相同错误文字不足以证明同根因；本机单次成功不能否定用户端间歇问题。

| 证据 | 处理 |
| --- | --- |
| 同一故障已复现且根因明确 | 在维护授权内最小修复；仅复现任务回传证据 |
| 确定性静态缺陷，有精确源码依据 | 授权修复时可先改并针对性验证；明确“未动态复现”，不能冒称现场已恢复 |
| 本次条件下未复现，且无独立充分缺陷证据 | 保留结果与条件差异，不靠猜测改业务逻辑 |
| 环境/账号/输入问题 | 解释证据和具体缺项，按授权处理，不靠修改定位掩盖 |
| 当前版已有修复 | 验证适用范围并说明版本差异，不重复补丁 |
| 动作结果未知 | 只对账；不切换定位、后端或运行通道重放 |

## 修改、验证与收尾

修改前按 [备份](application-git-backup.md) 保留受影响原文/结构，回读当前基线；漂移时先合并差异，不整份覆盖。按 [资产分类](asset-types.md) 加载适用开发规范，再通过正常客户端通道做最小修改。专用元数据维护采用其关闭设计器流程。

按 [验证交付](validation-and-delivery.md) 核验写入、静态、运行和业务结果；临时测试变更恢复并回读，只恢复本任务差异，保留正式修复及并发修改。只清理本任务资源。按 [报告](report-contract.md) 交付事实、证据和缺口；不把保存写成已同步/发布，不把本机通过写成用户端恢复。

执行细节需要核对时读 [操作约定](operating-rules.md)；相似问题分流可参考 [典型场景](scenarios.md)，无需每轮重复加载。
