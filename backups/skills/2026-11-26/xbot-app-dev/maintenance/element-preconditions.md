# 元素出现条件与前置步骤

用于"元素未找到 / 元素失效 / 定位失败 / UIAError Code:101 类"报错。核心原则：**先证明元素此刻应当出现，再讨论它为什么没找到。** 不得打开目标页面直接找元素就下结论。

## 为什么不能直接找元素

目标元素往往依赖业务状态：只有填完输入框、点了某个按钮、切了 tab、打开了弹窗、加载完成或进入某个列表/分页后，元素才进入 DOM 或无碍可交互状态。直接在初始页面上定位，找不到属正常现象，不能据此判定"页面改版 / 元素失效 / 定位器过期"。

同一个元素在不同状态下可能是不同节点（弹窗层、懒加载占位、虚拟列表），只改 XPath 不核对状态，等于把状态问题误修成定位问题。

## 分析顺序

1. **定位调用点**：从报错行、堆栈和调用链找到该元素所属的流程/函数与业务动作（如"查询关键词后取复制链接"）。
2. **读上游逻辑**：沿调用链向上，找出该元素出现依赖的前置动作与状态：
   - 输入类：输入框赋值、选择项、搜索关键词、参数带入；
   - 交互类：点击/展开/切 tab/翻页/滚动/打开弹窗、确认或关闭提示；
   - 数据类：列表加载完成、异步请求返回、loading 消失、分页或筛选生效；
   - 身份类：登录、店铺/租户切换、多窗口或 iframe 切换、路由跳转与 URL 参数。
3. **写前置序列**：把每步记成"动作 → 目标 → 参数 → 预期状态变化 → 可用什么证据确认"。序列必须来自代码/参数/日志，不靠猜测补步骤。
4. **对照用户端事实**：用户日志里的失败位置、输入、截图状态用于判断用户端执行到哪一步；用户端截图状态与本机不同，说明前置条件差异，不能据此否定用户端现象。

## 复现与验证

- 每次从获准的起点按"前置序列 → 到达目标状态 → 再定位元素"重新执行并核验；不能把先前已打开的网页或窗口、历史快照当成本次前置已完成。跳步直接找元素的结果无效；如必要前置不可安全重放，只对已验证部分作结论并说明缺口。若前置步骤由被测指令或上游正常流程自动完成，直接运行并通过日志或运行结果确认，不要求人工逐步操作或预先打开页面；只有实际入口需要外部页面对象时才准备该对象。
- 每步确认状态确实变化（快照/ref、URL、可见文本、日志），而不是"点完了就算"。
- 到达同一状态后仍找不到，才可进入定位失效评估；继续排除权限、渲染异常、frame 上下文错误和观察不完整，再判断是否为页面变更或定位失效。此时保留新旧定位候选与状态证据。
- 前置无法执行（缺测试数据、账号、环境、权限）→ `blocked`，写明缺哪一步，不能写成"未复现"或"元素不存在"。
- 前置动作有真实业务副作用（提交、发送、下单、发消息、改状态）时，按任务授权与重复安全判断；未获授权时用隔离/只读方式验证，或只做静态推导。

## 只读任务

只读调查不执行前置步骤，只允许：
- 静态推导前置序列，并标注"未运行验证"；
- 读取现有日志、快照、截图推断用户端当时状态；
- 报告元素出现条件的假设与缺口。

不得因为"没跑起来"就下"元素已失效"的结论，也不得把静态推导写成已复现。

## 与定位修复的边界

- 先确认出现条件，再评估定位器；状态不对时修改 XPath 属误修。
- 元素可能有多状态（未登录/已登录、空列表/有数据），修复需覆盖原故障状态且保持其他状态可用。
- 集合类元素要先满足列表加载与分页条件，再核对成员完整性，不能取第一个匹配代替目标。

## 回传写法

```text
元素：<页面/区块> 的 <元素描述>，定位方式 <xpath/css/元素库/ref>
出现条件：<前置步骤序列，逐步写明动作与状态>
实际状态：<本机/用户端到达的状态与证据>
结论：<前置缺失 / 状态不符 / 到达状态后仍缺失 / 未验证>
```

- 可写："按代码推导，该元素需在关键词查询返回结果并展开结果卡片后出现；本机未执行查询，直接定位失败，不能判定元素失效。"
- 不写："打开页面找不到该元素，所以元素已失效、需要改 XPath。"
